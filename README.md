# eva-mcp

MCP-сервер для работы с системой управления проектами **EvaProject** (EvaTeam).

Позволяет AI-агенту получать описание задач, комментарии, обновлять поля, работать со спринтами, требованиями, журналом работ и искать проекты/пользователей.

История выпусков — в [CHANGELOG.md](CHANGELOG.md).

## Возможности

| Инструмент | Описание |
|-----------|----------|
| `get_task` | Получить задачу по коду: название, описание, статус, автор, исполнитель, проект, даты, **иерархические комментарии (треды)** и упомянутые задачи |
| `search_tasks` | Поиск задач по фильтрам: статус, исполнитель, проект, приоритет, тип, текстовый запрос, спринт, даты, **linked_to**, **no_sprint**, **include_archived** |
| `count_tasks` | Подсчёт количества задач по фильтрам (те же фильтры, что и `search_tasks`) |
| `create_task` | Создать новую задачу в проекте |
| `update_task` | Обновление полей задачи (статус, исполнитель, приоритет, дедлайн, описание, спринты и др.) |
| `get_project` | Информация о проекте по коду |
| `search_projects` | Поиск проектов по названию |
| `search_users` | Поиск пользователей по имени, фамилии или логину |
| `get_statuses` | Справочник всех статусов задач с ID, названиями и кодами |
| `get_linked_tasks` | Связанные задачи: родительская, дочерние, depended, affected |
| `get_referencing_tasks` | **Обратный поиск связей**: кто ссылается на эту задачу (сгруппировано по типу связи) |
| `get_linked_tasks_batch` | **Батчевый get_linked_tasks**: связи для нескольких задач (до 50) за один вызов |
| `link_tasks` | **Установить связи** между задачами: depended, affected, local_links, parent_task. Merge-семантика (дополняет, не затирает) |
| `unlink_tasks` | **Удалить связи** между задачами: depended, affected, local_links, parent_task. Идемпотентен |
| `list_relation_types` | **Список типов связей** (CmfRelationOption): «Относится к», «Доп. дочерняя задача» и др. |
| `link_relation` | **Создать произвольную связь** (CmfRelationOption) — отображается в UI в разделе «Связи» |
| `unlink_relation` | **Удалить произвольную связь** — по ID, паре задач или типу |
| `get_task_worklog` | Журнал работ (timetracker) по задаче |
| `log_work` | Списать время по задаче |
| `get_task_history` | История изменения статусов задачи |
| `get_sprint` | Информация о спринте: название, статус, проект, даты, владелец, **признак архива и счётчики задач по статусам** |
| `search_sprints` | Поиск спринтов по проекту, статусу, текстовому запросу; **`include_archived` — закрытые спринты, счётчики задач в таблице** |
| `create_sprint` | Создать новый спринт (список) в проекте |
| `add_comment` | Добавить комментарий к задаче (Markdown) |
| `get_requirement` | Получить требование из EvaReq по коду |
| `search_requirements` | Поиск требований по статусу, исполнителю, проекту, приоритету |
| `update_requirement` | Обновить **черновик текста** требования по коду (Markdown) |
| `get_burndown_data` | Burndown спринта: идеальная и фактическая линии сгорания, тренд |
| `get_velocity` | Velocity команды по последним спринтам (включая закрытые) |
| `get_cycle_time` | Cycle time: время от создания до закрытия, перцентили |
| `get_cumulative_flow` | Cumulative Flow Diagram: распределение задач по статусам |
| `get_sprint_review` | Sprint Review: что сделано в спринте |
| `get_sprint_retrospective` | Sprint Retrospective: метрики спринта, что прошло хорошо и что нет |
| `get_team_workload` | Загруженность команды: задачи по исполнителям и статусам |
| `get_project_health` | Health Check проекта: спринты, доля закрытых, просрочки |
| `get_attachments` | Список вложений задачи по её коду |
| `get_task_followers` | Список подписчиков задачи |
| `search_docs` | **Wiki (EvaWiki)**: поиск страниц по названию, проекту или родительской странице |
| `get_doc` | **Wiki**: страница по коду DOC-XXXXXX, текст конвертируется в Markdown |
| `create_doc` | **Wiki**: создать страницу в проекте (Markdown → HTML, публикация через черновик) |
| `update_doc` | **Wiki**: заменить текст страницы (Markdown → HTML, черновик + `do_publish`) |

### Окно запроса: `limit` и `offset`

`search_tasks`, `search_sprints` и `search_requirements` принимают `limit` и `offset`.
Важно понимать, что это **окно запроса**: `offset` пропускает первые N записей, `limit`
задаёт, сколько запросить, а фильтр применяется к уже выбранному окну. Поэтому строк
может прийти меньше, чем есть совпадений, — вплоть до пустого ответа.

Инструменты об этом говорят прямо: в шапке видно `найдено` (истинное число, из
`count_*`) и `показано`, а если окно пустое — сколько совпадений за ним осталось.
Точные цифры берите из `count_tasks` / `count_sprints`, а списки — для показа.

### Закрытые спринты и их задачи

Закрытый спринт уходит в архив вместе со своими задачами: по умолчанию он не попадает
ни в `search_sprints`, ни в состав `search_tasks(sprint=...)`, причём без каких-либо
признаков, что часть данных скрыта.

- **`search_sprints`** принимает `include_archived: true` — в выдачу попадают закрытые
  спринты, помеченные 📦.
- **`search_tasks`** и **`count_tasks`** принимают `include_archived: true` — нужно,
  чтобы увидеть полный состав закрытого спринта.
- **`get_sprint`** архивные спринты отдавал и раньше; теперь показывает признак архива.

Счётчики задач по статусам (всего / открыто / в работе / на ревью / закрыто) есть в
`get_sprint` и `search_sprints`: API отдаёт их вместе с остальными полями спринта,
дополнительных запросов не требуется. У живых спринтов счётчики совпадают с фактическим
составом, у архивных перестают обновляться: сумма обычно верна, а разбивка по статусам —
снимок на момент архивации, поэтому к таким спринтам в выдаче добавляется предупреждение.

### Wiki (EvaWiki)

Страницы wiki — это `CmfDocument`, адресуются кодом `DOC-XXXXXX`. Что полезно знать:

- **Место в дереве навигации задаёт `tree_parent`, а не `parent`.** `parent` — это раздел
  страницы, и у страниц wiki это проект; в дереве, которое видно в интерфейсе, страницу
  держит `tree_parent`. `create_doc` с параметром `parent` ставит страницу под указанную
  страницу, без него — в корень wiki проекта; `get_doc` показывает раздел и место в дереве
  отдельными строками.
- Вложенная фильтрация по `CmfDocument.parent` на стороне API запрещена (ответ `-32001`,
  «Недопустимый тип поля для вложенной фильтрации»), поэтому иерархия ищется по
  `tree_parent.code`, а принадлежность проекту — по `project.code`.
- Текст записывается только через черновик `text_draft` с публикацией методом `do_publish`:
  прямая запись в `text` отклоняется API.
- `get_doc` обрезает длинные страницы (`max_chars`, по умолчанию 30000) — в wiki
  встречаются страницы на сотни килобайт.

### Читающие и пишущие инструменты

Инструменты делятся на две группы, и это стоит учитывать, когда сервер подключают агенту:

- **Читают**: `get_*`, `search_*`, `count_*`, `list_relation_types`.
- **Пишут в EvaTeam**: `create_task`, `update_task`, `add_comment`, `log_work`,
  `create_sprint`, `link_tasks`, `unlink_tasks`, `link_relation`, `unlink_relation`,
  `create_doc`, `update_doc`, `update_requirement`.

Отдельного режима «только чтение» у сервера нет: доступны оба набора, а пределы задаёт
токен. Если агенту запись не нужна, надёжнее оговорить это в его инструкции и выдать токен
аккаунта с подходящими правами, чем рассчитывать на сервер.

## Установка

Готовый пакет ставить не нужно: MCP-клиент запускает сервер сам.

```bash
npx -y eva-mcp
```

Для работы с исходниками — обычная установка зависимостей:

```bash
npm install
```

## Настройка

Серверу нужны две переменные: **EVA_URL** — адрес вашего инстанса EvaTeam (например,
`https://your-company.evateam.ru`) и **EVA_TOKEN** — API-токен. Задавать их в конфиге
MCP-клиента не обязательно: сервер ищет их сам, по цепочке, первый непустой источник
побеждает:

1. переменные окружения процесса — если клиент передал их явно;
2. `./.env` в рабочей папке — локально для этого проекта;
3. `~/.eva-mcp` в домашней папке — умолчание для всех проектов;
4. `.env` в корне пакета — только если сервер запущен из клона репозитория.

**Самый простой путь:** запустите сервер один раз без настройки — он создаст
`~/.eva-mcp` с шаблоном и попросит его заполнить:

```
# eva-mcp: учётные данные EvaTeam. Заполните и перезапустите MCP-клиент.
EVA_URL=
EVA_TOKEN=
```

Заполните и перезапустите MCP-клиент — больше ничего делать не нужно, из какого бы
клиента и проекта сервер ни запускался. Файл в формате `.env`; на POSIX он создаётся
с правами `0600`.

Нужен другой токен в конкретном проекте — положите рядом `.env` с теми же двумя
переменными: он перекроет `~/.eva-mcp` только в этой папке. При старте сервер пишет
в stderr, откуда взял каждую переменную (имена источников, не значения).

Если клиент показывает только «Failed to connect», сообщение сервера — в его логе.
Claude Code складывает stderr серверов в
`%LocalAppData%\claude-cli-nodejs\Cache\<проект>\mcp-logs-eva-mcp\` (строки
`Server stderr: …`); проще всего запустить ту же команду из конфига прямо в терминале —
сервер напечатает, что создал и где искал.

### Как получить API-токен

1. Авторизуйтесь в EvaTeam
2. Нажмите на аватар → **Моя страница**
3. Перейдите на вкладку **Безопасность**
4. Нажмите **Сгенерировать API токен**
5. Укажите имя токена и срок жизни, нажмите **Создать токен API**
6. Скопируйте токен и сохраните в `.env`

> ⚠️ Токен показывается только один раз. При утрате нужно сгенерировать новый.

## Проверка

```bash
npm run check    # типы + состав инструментов сверяется с документацией
npm run smoke    # сборка + старт сервера по stdio: число инструментов и дубли
npm run probe -- --list                                          # инструменты на живом сервере
npm run probe -- --tool get_task --args '{"code":"DEV-000003"}'   # живой вызов
```

`check` и `smoke` обязательны перед PR. `probe` требует `.env` с `EVA_URL` и `EVA_TOKEN` и ходит
на живой инстанс: читать можно на любом проекте, писать — только в тестовый.

## Подключение MCP-сервера

Сервер клиент-агностичен — это обычный stdio MCP-сервер, его регистрирует любой
клиент, поддерживающий MCP. Если сервер поставлен из npm, в конфиге достаточно `npx`:

```json
{
  "servers": {
    "eva-mcp": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "eva-mcp"]
    }
  }
}
```

Если сервер запускается из исходников, соберите его (`npm run build`) и укажите путь
к `dist/index.js`:

```json
{
  "servers": {
    "eva-mcp": {
      "type": "stdio",
      "command": "node",
      "args": ["/путь/до/eva-mcp/dist/index.js"]
    }
  }
}
```

Именно так настроен сам репозиторий: готовые конфиги для двух клиентов лежат в нём
(форматы разные, сервер один) и указывают на локальную сборку — редактор работает
с тем кодом, что в рабочей копии.

| Клиент | Файл в репозитории | Ключ верхнего уровня |
|--------|--------------------|----------------------|
| VS Code Copilot | `.vscode/mcp.json` | `servers` |
| Claude Code | `.mcp.json` (project-scope) | `mcpServers` |
| Cursor и другие | конфиг клиента | по документации клиента |

Учётные данные сервер берёт из переменных окружения `EVA_URL` и `EVA_TOKEN`, а если
их нет — из файла `.env` в корне пакета (рабочая папка может быть любой). Задавать
их в конфиге клиента не нужно, если `.env` лежит рядом с пакетом.

## Инструкции для ИИ-агентов

Инструкции для ИИ-агентов лежат в `AGENTS.md` (корень), `src/AGENTS.md` (API-слой)
и `src/tools/AGENTS.md` (MCP-инструменты). VS Code Copilot читает корневой файл
напрямую, Claude Code — через `CLAUDE.md`: это загрузчик из трёх строк импорта тех
же файлов. Вложенные файлы агент читает по предписанию из корневого `AGENTS.md`.

## Пример использования

В диалоге с агентом:

> Посмотри задачу DEV-000123 и напиши код согласно описанию

Агент вызовет `get_task("DEV-000123")`, получит описание и комментарии, и использует их как ТЗ.
